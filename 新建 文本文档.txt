  Files: rust/vmp-core/src/vm/arch.rs, assembler.rs, compiler.rs

  - Generate a separate handler for each condition code in assembler.rs
  - Preserve the condition in extract_core_opcode()

  Backward jumps (jump to a label appearing earlier in bytecode) may still have key mismatch at the jump target, since
  the compiler's linear key and the runtime VKEY from the jump site differ. This doesn't cause crashes (the decrypted
  value stays in 0-255 range) but may cause wrong handler dispatch at the target. This is a pre-existing issue not

● Build successful. Let me summarize the two bugs I found and fixed:

  Bug Analysis

  Bug 1 (Crash cause): Rolling Key Desync in VJmp/VJcc

  File: rust/vmp-core/src/vm/handlers.rs

  The compiler (compiler.rs) does NOT update current_key when processing VJmp/VJcc jump offsets. However, the runtime
  handlers were updating VKEY with the decrypted offset value. This caused the rolling key to drift by exactly the jump
  offset amount on every VJcc/VJmp.

  In the trace, after a VJcc fallthrough, the next opcode decrypted to 0x1B7 (439) instead of a valid 0-255 handler
  index, causing jmp [table + 439*8] to read from the bytecode region (past the 256-entry handler table), jumping to
  garbage data → crash.

  Fix: Removed VKEY += offset from both gen_vjmp() and gen_vjcc() handlers. Jump offsets are used only for VIP
  adjustment, not for the cryptographic chain. This matches the compiler's behavior.

  Bug 2 (Logic error): All VJcc conditions treated as Z

  Files: rust/vmp-core/src/vm/arch.rs, assembler.rs, compiler.rs

  Only one VJcc handler was generated — always using condition=0 (cmovz/ZF). This meant all conditional jumps (JNE, JB,
  JG, etc.) were checked against the wrong flag, causing incorrect branch decisions.

  Fix:
  - Added 16 VJcc variants (VJcc(0..=15, 0)) to core_ops in arch.rs
  - Generate a separate handler for each condition code in assembler.rs
  - Preserve the condition in extract_core_opcode()

  Remaining concern

  Backward jumps (jump to a label appearing earlier in bytecode) may still have key mismatch at the jump target, since
  the compiler's linear key and the runtime VKEY from the jump site differ. This doesn't cause crashes (the decrypted
  value stays in 0-255 range) but may cause wrong handler dispatch at the target. This is a pre-existing issue not
  introduced by this fix.
