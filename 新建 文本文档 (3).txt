Collision）漏洞。

🐞 深度漏洞分析：双栈冲撞塌陷

在我们的 VMP 设计中，存在两个关键的栈指针：

1.  Native RSP：用来追踪原本宿主函数的栈底。当源码中有 char dst[256]; 这种局部变量时，编译器会 sub rsp, 256，此时
    Native RSP 就会往下生长。
2.  VSP (Virtual Stack Pointer)：虚拟机自己用来进行 VPush / VPop 计算的虚拟栈。

如果你看一下 gates.rs 原本的代码，你会发现它对虚拟栈的分配极其危险：

asm.mov(ctx.vsp, rsp)?;
asm.sub(ctx.vsp, 136_i32)?; // VSP 紧贴着 Native RSP 的下方！
asm.sub(rsp, 0x2000_i32)?;  // CPU RSP 移动到 8KB 之外

灾难发生过程： VSP 初始化在 Native RSP - 136 的位置。一旦你的原生代码里申请了一个超过 136 字节的局部数组（比如 char
dst[256]），原生代码执行 VWriteMem 去向 dst 写数据时，它会直接写进虚拟机自己的 VSP 栈里！
这会当场覆盖掉虚拟机正在计算的中间变量，导致下一次 VPop
弹出垃圾数据，随后解密出无法识别的 Opcode 并向随机的内存地址乱飞，最后死在 ntdll 里。

🛠️ 系统级修复方案：隔离双栈

我们需要在进入虚拟机时（gen_vmentry 和 gen_vm_reentry），开辟一片足够大（比如 64KB）的沙盒内存，并将 Native Stack
和 VM Stack 从物理布局上彻底切开，互不侵犯。

请修改 rust/vmp-core/src/vm/gates.rs 文件中的这几处：

1. 修改 gen_vmentry (进入虚拟机)

<<<<
        // 2. 初始化虚拟上下文
        // VSP 初始化为 RSP_entry - 136 (与旧版语义一致，留出空间)
        asm.mov(ctx.vsp, rsp)?;
        asm.sub(ctx.vsp, 136_i32)?;
        // 分配 VM 栈空间 (在原生栈上)
        asm.sub(rsp, 0x2000_i32)?;
====
        // 2. 初始化虚拟上下文
        // 分配 64KB 的终极安全沙盒，彻底隔离 Native 栈与 VM 栈
        asm.sub(rsp, 0x10000_i32)?;

        // VSP 初始化为 CPU RSP + 0x8000 (位于 64KB 缓冲区的绝对正中间)
        // 这样布局意味着：
        // 1. 原生代码的局部变量 (Native RSP) 可以从最顶端向下安全生长整整 32KB。
        // 2. 虚拟机自身的计算栈 (VSP) 从中间向下安全生长 32KB。
        // 两者被物理隔离，彻底解决字符串/大数组覆盖 VMP 内部状态的梦魇！
        asm.mov(ctx.vsp, rsp)?;
        asm.add(ctx.vsp, 0x8000_i32)?;
>>>>

2. 修改 gen_vm_reentry (API 调用重入桩)

<<<<
        // 2. 分配 VM 栈空间
        asm.sub(rsp, 0x2000_i32)?;
====
        // 2. 分配 64KB 的终极安全沙盒
        asm.sub(rsp, 0x10000_i32)?;
>>>>

💡 为什么这么改不会内存泄漏？

你可能会担心，每次进入 VM 和重入都 sub rsp, 0x10000，会不会把堆栈干爆？ 不会。 因为在 handlers.rs 的 VExit 和
VCall 逻辑中，我们已经写了绝杀逃逸跳板（self.asm.mov(rsp, qword_ptr(r15 + 24_i32))）。每次返回宿主 API
或是退出保护区块时，CPU 的真实 RSP 都会被精准回溯还原到最开始的 Native RSP 状态。所以这 64KB
会在执行完成后完美释放，一滴都不漏。
